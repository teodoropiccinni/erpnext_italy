# Italian E-Invoicing — Feature Design

This document describes the design of the SDI e-invoice import features in `erpnext_italy`.
It is the canonical reference for developers working on the import pipeline.

---

## 1. Italian E-Invoicing Overview

Italy mandates electronic invoicing via the **SDI (Sistema di Interscambio)**, the Italian
Revenue Agency's exchange hub. All B2B and B2G invoices must be transmitted through SDI in
the **FatturaPA** XML format (schema version 1.2, namespace
`http://ivaservizi.agenziaentrate.gov.it/docs/xsd/fatture/v1.2`).

### Flow

```
Supplier                 SDI                   Buyer
   │                      │                      │
   │── FatturaPA XML ──►  │                      │
   │                      │─── delivery ZIP ──►  │
   │                      │◄── RC receipt ───────│
   │◄── outcome notif ────│                      │
```

The delivery ZIP sent to the buyer contains:
- `<filename>.xml` — plain FatturaPA XML (sometimes omitted)
- `<filename>.xml.p7m` — CAdES-BES signed wrapper around the same XML (always present)
- `<filename>_RC_NNN.xml` — Ricevuta di Consegna (delivery receipt, SDI-generated)
- Optionally `<filename>_NS_NNN.xml` — Notifica di Scarto (rejection notice)
- Optionally `<filename>_MC_NNN.xml` — Mancata Consegna (failed delivery notice)

The `_RC_`, `_NS_`, `_MC_` files are **SDI notifications**, not invoices. Their XML
structure is completely different from FatturaPA and must be skipped by the importer.

## 2. File Formats

### 2.1 Plain XML (`.xml`)

Standard UTF-8 or UTF-16 encoded FatturaPA XML. Directly parseable with BeautifulSoup.

### 2.2 Signed XML (`.xml.p7m`)

A DER-encoded **CMS SignedData** (PKCS#7 / RFC 5652) envelope using the CAdES-BES profile.
The inner payload is the raw FatturaPA XML bytes stored as the `eContent` of the
`EncapsulatedContentInfo` structure.

Structure:
```
ContentInfo (DER)
└── SignedData
    ├── version
    ├── digestAlgorithms
    ├── encapContentInfo
    │   ├── eContentType  OID 1.2.840.113549.1.7.1 (id-data)
    │   └── eContent      OCTET STRING → raw FatturaPA XML bytes
    ├── certificates      (signer cert chain)
    └── signerInfos       (signature over eContent)
```

Extraction is done by `erpnext_italy/utils/p7m.py` using `asn1crypto`. Signature
verification is **not performed** — Italian law allows import regardless of cert validity.

## 4. Three Import DocTypes

### 4.1 `Purchase Invoice IT SDI Import`

**Use case:** Standard inbound supplier invoices received from SDI.

- Reads `CedentePrestatore` as the **Supplier**
- Creates a **Purchase Invoice** in ERPNext
- Accepts all standard TipoDocumento values

**When to use:** Your company receives invoices from Italian suppliers via SDI.

---

### 4.2 `Sales Invoice IT SDI Import`

**Use cases:**
1. **Software migration** — importing historical sales invoices generated by another
   invoicing system (e.g. Fatture in Cloud, TeamSystem) to align ERPNext records.
2. **SDI reconciliation** — matching SDI-sent invoices against ERPNext records to update
   `einvoice_status` custom fields.

- Reads `CessionarioCommittente` as the **Customer**
- Creates a **Sales Invoice** in ERPNext

**When to use:** Transitioning from another invoicing platform and need to replay past
sales invoices into ERPNext, or reconciling SDI outcomes against existing invoices.

---

### 4.3 `Foreign Purchase Invoice IT SDI Import`

**Use case:** **Autofattura** — self-invoices the company must issue when receiving
services or goods from foreign suppliers not registered in Italy.

- Reads `CedentePrestatore` as the **foreign Supplier** (informational)
- The company invoices itself: the **Customer** on the Sales Invoice is the company itself
- Creates a **Sales Invoice** (registered in the sales register / *registro vendite*)
- **Hard filter:** only processes files with `TipoDocumento` in `{TD17…TD27}`. Files with
  other codes are logged and skipped without raising an error.

**When to use:** Integrating foreign services (consulting, SaaS, etc.) where Italian VAT
reverse-charge or self-invoicing obligations apply.

## 5. Shared Base Class

All three DocTypes inherit from `SDIImportBase` in
`erpnext_italy/utils/sdi_import_base.py`.

### Responsibilities of the base class

| Method / Function | Purpose |
|---|---|
| `import_xml_data()` | Opens ZIP, iterates files, calls `prepare_data_for_import` |
| `prepare_items_for_invoice()` | Parses `DettaglioLinee` line items (shared) |
| `process_file_data()` | Whitelisted — enqueues `import_xml_data` as background job |
| `publish()` | Realtime progress via `frappe.publish_realtime` |
| `_is_invoice_file(name)` | Returns `True` only for `.xml` / `.xml.p7m`, skips `_RC_` etc. |
| `get_file_content(name, zf)` | Reads ZIP entry; calls `extract_xml_from_p7m` for `.p7m` |
| `get_supplier_details(xml)` | Extracts party info from `CedentePrestatore` |
| `get_customer_details(xml)` | Extracts party info from `CessionarioCommittente` |
| `get_taxes_from_file(xml, account)` | Parses `DatiRiepilogo` VAT rows |
| `get_payment_terms_from_file(xml)` | Parses `DettaglioPagamento` rows |
| `get_destination_code_from_file(xml)` | Reads `CodiceDestinatario` from header |
| `create_supplier(group, args)` | Upserts Supplier + Contact |
| `create_customer(group, args)` | Upserts Customer |
| `create_address(party_type, name, args)` | Upserts billing Address |
| `create_uom(uom)` | Upserts UOM |
| `get_country(code)` | Resolves ISO country code to ERPNext Country name |

### What subclasses must implement

```python
def prepare_data_for_import(self, file_content, file_name, encoded_content):
    # 1. Iterate file_content.find_all("DatiGeneraliDocumento")
    # 2. Extract party (supplier or customer)
    # 3. Call self.prepare_items_for_invoice(file_content, invoices_args)
    # 4. Call get_taxes_from_file / get_payment_terms_from_file
    # 5. Create or upsert the party record
    # 6. Create the ERPNext invoice document
    # 7. Increment self.file_count and self.invoice_count
```

## 7. Processing Pipeline

```
User uploads ZIP → clicks "Import Invoices"
         │
         ▼
process_file_data()          [whitelisted, runs in HTTP request]
  └── enqueue import_xml_data as background job (queue=long, timeout=3600)

import_xml_data()            [background worker]
  ├── Open ZIP
  ├── For each file in ZIP:
  │     ├── _is_invoice_file()?  No → skip (_RC_, _NS_, _MC_, other)
  │     ├── get_file_content()
  │     │     ├── .xml  → decode UTF-8/UTF-16
  │     │     └── .xml.p7m → extract_xml_from_p7m() → decode
  │     └── prepare_data_for_import()   [subclass]
  │           ├── Find DatiGeneraliDocumento nodes
  │           ├── [ForeignPurchase only] check TipoDocumento ∈ AUTOFATTURA_TYPES
  │           ├── Extract party info (supplier / customer)
  │           ├── prepare_items_for_invoice()
  │           ├── get_taxes_from_file()
  │           ├── get_payment_terms_from_file()
  │           ├── create_supplier() / create_customer()
  │           ├── create_address()
  │           ├── _create_purchase_invoice() / _create_sales_invoice()
  │           └── save_file() — attach original XML/P7M to the created invoice
  ├── Compute status: "File Import Completed" or "Partially Completed - Check Error Log"
  └── save() + publish realtime progress
```

## 8. Error Handling

| Situation | Behaviour |
|---|---|
| P7M extraction fails | `frappe.log_error` + returns `""` → file skipped, count mismatch flags partial completion |
| UTF decode fails | `frappe.log_error` + returns `""` → same as above |
| Invoice creation fails | `frappe.log_error` + sets status to `"Error"` on the import doc + returns `None` |
| Non-autofattura doc type in foreign import | `frappe.log_error` + `continue` (not an error, just logged) |
| Country code not found | `frappe.throw` — hard stop, user must fix country setup |
| Missing UOM | Auto-created via `create_uom()` |
| Supplier/Customer already exists | Matched by `tax_id` first, then by name — no duplicate created |
